# 股票信号系统 · 知识架构体系

> 研究时间：2026-07 | 文档类型：项目知识手册 | 读者画像：Java 工程师

## 〇、这份文档是写给谁的

写给一个 Java 工程师——也就是你。这套系统从需求讨论到上线部署，全程是我（AI）主导开发、你审核决策完成的。过程中出现了大量名词：MyBatis、TA4J、akshare、前复权、幂等、Caddy、systemd、CSP、fail2ban、PushPlus、Vue、ECharts……Java 侧的你熟，其余的你只是一面之交。

这份手册的目的只有一个：让你在不问任何人的情况下，完全看懂自己的系统。每一个术语我都会回答三个问题——它是什么、为什么选它、它在项目里蹲在哪个角落。能拿 Java 生态类比的，我一律用 Java 类比，因为那才是你的母语。

先给你一张全景。整个系统只有五个部分：

```
┌─────────────┐   写库   ┌──────────┐   读库   ┌──────────────────┐
│ fetch/      │ ──────→ │  MySQL 8 │ ←────── │ stock-server     │
│ Python 取数  │         │ 5 张表    │         │ (Spring Boot 3)  │
│ (akshare)   │         └──────────┘         │  ├ stock-engine   │
└─────────────┘                              │  │ (纯库,指标+策略)│
                                             │  ├ DailyRun 编排   │
                                             │  ├ REST API       │
                                             │  └ 静态页面托管    │
                                             └──────┬───────┬───┘
                                              微信推送│       │HTTP
                                             PushPlus│       │
                                                    ↓       ↓
                                              你的微信    浏览器(Vue3+ECharts)
```

一句话定义这套系统：**每日收盘后，自动扫描沪深300加自选股票池，用可配置的技术策略（KDJ金叉死叉等）筛出候选股，生成页面大屏并推送微信通知的批处理系统。**

它不是实时系统，不盯盘，不做高频。它每天只工作一次，但每次工作都必须做对——这个定位决定了后面几乎所有的技术决策。

## 一、纵向：这套系统是怎么一步步长出来的

### 1.1 需求拷问期：三个最底层的决策

项目不是从写代码开始的，是从一连串"为什么"开始的。这三个决策定下了整个系统的骨架，后面的所有代码都只是填充。

**决策一：Java 主体 + Python 边车，而不是全 Java 或全 Python。**

你的第一反应可能是"我懂 Java，全 Java 干"。这条路被否掉的原因很硬：免费的行情数据源生态几乎全在 Python 里。akshare 这个库（后面会细讲）本质上是把东方财富、新浪这些网站的非公开接口封装成了 Python 函数，沪深港美四个市场的日线数据一行调用就能拿到。Java 侧没有等价物——用 Java 就意味着自己维护对东财网页接口的逆向抓取，那些接口没有文档、会变、会封 IP，维护成本全落在你一个人身上。

但全 Python 也不对：你是 Java 工程师，核心引擎（指标计算、策略评估、API、定时任务）用你不熟的语言写，迭代慢、质量差、开源后还吸引不到你同温层的贡献者。

最后的形态是**混合架构**：数据抓取是一个两百行的 Python 脚本（这种代码 AI 生成、你照抄运行即可，不需要"会 Python"，只需要"能跑 Python"），剩下 95% 的代码全是你主场的 Java。两边通过数据库解耦——Python 只管把数据写进 MySQL，Java 只管从 MySQL 读，互不见面。

这里有个架构上的关键手法，后面反复出现：**数据获取层被抽象成一个接口（`MarketDataProvider`），Python 脚本只是这个接口背后的第一个实现。** 哪天你想纯 Java 化、或者买付费数据源（Wind、Tushare Pro），换掉的是实现，不是架构。

**决策二：指标自己算，不拷贝别人的。**

既然要算 KDJ 金叉死叉，能不能直接从某个网站把算好的 KDJ 值拿过来？不能，原因有三层。第一，免费渠道根本没有"现成指标值"这种稳定产品。第二，KDJ 就是 RSV 的两次指数平滑，十几行数学，自己算成本约等于零。第三，也是最要命的——拷贝来的指标参数是死的。这个产品的定位是"可配置策略的信号引擎"，你的用户（包括你自己）迟早要调参数（KDJ 的 9,3,3 只是市场默认值），要加过滤条件，要做回测。**指标计算能力就是信号引擎的心脏，外包出去等于产品没有心脏。**

**决策三：Java 在量化领域生态错配，但对这个项目依然是正确选择。**

实话实说，量化交易社区的主流语言是 Python，Java 在这个领域没有它擅长的优势场景（高并发、大型企业集成）。但这个项目的差异化不在数据层、不在指标层，而在"信号引擎 + 通知触达"——这是标准的企业应用形态：定时批处理、数据库、REST API、权限认证。这是 Spring Boot 的主场。而且后续要加的 AGENT 分析（爬新闻、喂给 LLM 判断市场影响），Java 侧有 Spring AI 和 LangChain4j 两个成熟框架，LLM 应用层本质是 HTTP 调用加 Prompt 组装，语言无关。

我的判断是：语言选择从来不是"哪个语言最适合这个领域"，而是"哪个语言让主要维护者最高效"。这个项目的第一维护者是你。

### 1.2 骨架期（M0-M2）：多模块、纯库引擎、手写中式 KDJ

**Maven 多模块。** 项目一开始就是四个模块：`stock-data`（数据模型+数据库访问）、`stock-engine`（指标+策略，纯库）、`stock-server`（Web 服务）、`fetch/`（Python 脚本）。为什么不是一个大单体？因为 `stock-engine` 被刻意设计成**不依赖 Spring、不依赖数据库的纯 Java 库**——它的契约是"给定 K 线序列和策略配置，输出信号"，里面不允许出现"每天""定时""batch"这类词。这个约束当时看着是洁癖，后来证明是神来之笔：引擎可以脱离 Spring 单独跑单元测试，未来做盘中实时信号、做回测、做 AGENT 分析，引擎都是原封不动拿过去用的那个核。

**手写中式 KDJ，不用现成库。** Java 侧有个成熟的技术指标库叫 TA4J，但它实现的是**西式**随机指标（Stochastic）：%D 是 %K 的 3 日简单移动平均。而你父亲在东财上看到的 KDJ 是**中式**口径：K 和 D 都是 `SMA(X, N, 1)` 递推平滑（`K = (当日RSV + 2×前日K) / 3`），还有个 J = 3K - 2D。两种口径算出来的交叉日期会对不上——而验收标准是"与东财交叉日期一致"。所以 KDJ 是手写的，二十行，TA4J 依赖保留着给未来其他指标用。

这个决策反映了一个量化系统里最容易被忽视的问题：**同名指标在不同软件里的计算口径经常不一样，做信号系统必须先"冻结语义"再写代码。** 项目的 `docs/architecture.md` 里有一节专门冻结了 KDJ 的完整语义：前复权输入、9,3,3 参数、K/D 初值 50、窗口不足不出信号、金叉要求交叉日 K ≤ 20、死叉要求 K ≥ 80。这节文字比代码更早存在。

### 1.3 端到端期（M3-M4）：批处理的两个第一性原理

**幂等（Idempotency）**。这是整个批处理系统最重要的一条设计原则，没有之一。幂等的意思是：同一个操作执行一次和执行 N 次，效果完全一样。为什么它这么重要？因为批处理一定会重跑——抓取失败要重跑、部署更新要重跑、手动调试要重跑。如果重跑一次就重复产生一批信号、重复推送一批微信，这个系统就没人敢碰了。

项目里的幂等落在三个具体设计上：

- `signals` 表的唯一约束 `(market, code, trade_date, strategy, strategy_version, signal_type)`，插入用 `INSERT IGNORE`——重跑撞唯一键，数据库层面直接忽略，重复信号在物理上不可能存在。
- `strategy_version` 字段：策略参数改了版本号就变，历史信号永远能回答"它是哪版参数算出来的"。
- 通知层只在"本次有新增信号"时推送。重跑没有新增，就不打扰你。

**可追溯（Observability）**。自动化系统必须能回答"上次成功是什么时候、哪一步挂了"。项目里有一张运维表 `job_run`，DailyRun 的四个阶段（FETCH 抓取 → VALIDATE 校验 → EVALUATE 评估 → NOTIFY 推送）每个阶段都记录状态、时间、统计、错误。页面顶部那条"SH ✓ 数据至 2026-07-24"的状态条就是读这张表渲染的。

四阶段之间的依赖关系是硬性的：FETCH 或 VALIDATE 失败，就不计算、不推正常信号，改推一条失败告警。**宁可某天没有信号，也不能给用户发基于残缺数据的信号。**

**前端：薄页面 + REST 契约。** 页面是单个 HTML 文件（后来拆出 app.js），Vue 和 ECharts 直接从本地 vendor 目录加载，没有 npm、没有构建链。为什么这么"寒酸"？因为前端的定位是 REST API 的一个薄客户端——API 才是契约，页面只是消费者。将来要换 Vue3 工程化、要做小程序，后端 API 一个字不用改，旧页面整个扔掉换新壳就行。前端越薄，替换成本越低。

### 1.4 扩容期（M5-M7）：免费数据源的真实世界

沪深300 扩容时撞上了这个项目最真实的一个麻烦：**东财的反爬限流**。

免费数据源的"免费"是有代价的——东财的 kline 接口对 IP 有反爬策略，连续请求会直接把连接重置。我们实测了完整的生命周期：抓几只票没问题，连续抓就被封，封几个小时自动解，解了再抓再封，而且封禁还分客户端指纹（同一 IP 上 curl 能连、Python 的 requests 就连接重置，这是 TLS 指纹级别的识别）。

对策是三层。第一层，**多源切换**：A 股数据东财、新浪、腾讯三个源，批量脚本带"健康记忆"——东财连续失败两次后自动把新浪提到首选，不再每次白等退避时间。腾讯源是实战中意外发现的救兵，数值和新浪完全对齐。第二层，**限速加退避**：每个请求间隔 2.5 秒，失败按 5s/10s/20s 指数退避重试三次。第三层，**断点续灌**：所有写入都是 upsert 幂等，脚本中断后重跑从断点继续。最终 300 只股票、21 万行数据，一次跑通零失败。

这段经历值得记住的结论是：**用免费数据源，"限流"不是异常而是常态，抓取层必须把容错做成设计的一部分，而不是出了事再补。**

### 1.5 部署与安全期：教科书不会告诉你的四个坑

上云部署阶段连踩四坑，每一个都是真实世界的典型教材。

**坑一：systemd 不认 export。** 应用起不来，查了半天发现 systemd 的 `EnvironmentFile` 把 `export DB_URL=...` 整行忽略——它只认裸的 `KEY=VALUE`，不认 shell 的 export 前缀。Java 用默认值 `stock/stock` 去连真实密码的数据库，启动即崩。这类"两种配置体系格式不兼容"的坑，文档里不会写，只有踩过才知道。

**坑二：CSP 拦内联脚本。** 安全加固时加了 CSP 响应头（Content-Security-Policy，后面细讲），`script-src` 没放行内联脚本，而页面全部逻辑都是内联 `<script>`——浏览器把整个 Vue 应用拦死，登录按钮点了毫无反应。修复方式是把脚本抽到外部文件。

**坑三：CSP 拦 eval。** 修完坑二又白屏，这次是 Vue 的模板编译器运行时要用 `new Function()` 编译模板，CSP 默认禁 eval。放行 `'unsafe-eval'` 才解决。连续两个 CSP 坑说明一件事：**安全响应头不是加上就完事，必须和应用的实际形态匹配着配，配完必须在真实浏览器里验证一遍。**

**坑四，也是最严重的一次：root 被暴力破解。** 上线第三天，腾讯云告警：一个德国 IP 用 1630 次尝试把 root 密码爆破了，成功登录，翻了 5 分钟文件，读走了 `env.sh`（里面是数据库密码、推送 token、页面口令）。根因是绑定 SSH 密钥时密码认证没有关闭。

事后处置是一套完整的应急响应：关闭密码认证（只留密钥）、装 fail2ban（失败 5 次封 24 小时）、轮换全部密码和 token、排查后门（没有植入）、最终重装系统。这次事件换来的认知是：**暴露在公网的机器，22 端口被扫是每天都有的事，"密码强度还行"不是防线，"密码登录根本不存在"才是。**

### 1.6 纵向小结

回看这条时间线，系统的每个关键特性都能追溯到一次具体的决策或事故：幂等来自"批处理必然重跑"的推演，三源切换来自东财封 IP 的实战，密钥认证来自真实的入侵。这套系统不是被"设计"出来的，是被一个个具体的问题"逼"出来的——这其实是大多数好系统的真实成长方式。

## 二、横向：技术栈逐项拆解

下面按分层把每个技术名词讲透。格式统一：是什么 → 为什么选它 → 在项目哪里 → 替代方案是什么。

### 2.1 后端层（你的主场，快速过）

**Spring Boot 3。** 你熟。选它不选 Quarkus/Micronaut 的理由：你熟、生态最大、Spring AI 也在同一个屋檐下（后面 AGENT 分析要用）。项目里它是 stock-server 的骨架，跑 REST API、定时任务入口、依赖注入。

**Maven 多模块。** 你熟。parent pom 管版本，三个子模块各自打包。注意一个工程细节：`mvn -pl stock-server spring-boot:run` 之前必须先 `mvn install`，因为 `-pl` 单独构建时兄弟模块的 SNAPSHOT 要从本地仓库解析。这个坑我们在 M0 就踩过。

**MyBatis（而不是 JPA/Hibernate）。** MyBatis 是 SQL 映射框架：你写 SQL（在 XML 或注解里），它负责把结果集映射成 Java 对象。JPA 是对象关系映射：你操作对象，它替你生成 SQL。选 MyBatis 的理由有三：你本来就熟；这个项目的 SQL 都很简单直接（主键查询、区间查询、INSERT IGNORE），不需要 ORM 的对象状态管理那套复杂东西；批量写性能场景下，手写 SQL 的行为完全可控、没有 JPA 的 N+1 和缓存意外。项目里的分工是：**业务代码只依赖 Mapper 接口，SQL 全部收在 `stock-data/src/main/resources/mapper/*.xml`**——这是架构红线之一，保证未来换数据库实现（比如开源后给用户 SQLite 选项）只动 Mapper。

**MySQL 8。** 你熟。数据量坦白说很小（全市场三年也就几百万行），SQLite 都够用，选 MySQL 纯因为你熟——工具链熟练度大于理论最优。两个部署细节：生产环境只监听 127.0.0.1（不对公网开放）；应用账号 `stock` 只有 `stock_signal.*` 一个库的权限（最小授权）。

**HikariCP。** Spring Boot 默认的数据库连接池，你不需要配置它，但要知道它存在：应用不自己 new 数据库连接，而是从池里借。`Failed to obtain JDBC Connection` 这种报错就是从它这层抛出来的。

**springdoc-openapi。** API 文档生成器：扫描 Controller 上的 `@Operation`/`@Tag` 注解，自动生成 OpenAPI 规格和 Swagger UI 页面（`/swagger-ui.html`）。选它的核心理由是**防止文档漂移**——文档从代码注解生成，代码改了文档自动跟着变，不存在"文档是文档、代码是代码"的两张皮问题。项目规定接口改动必须同步维护注解，写进了 AGENTS.md 的硬规则。

### 2.2 引擎层（这个系统的心脏）

**TA4J。** Java 的技术分析指标库（MovingAverage、RSI、MACD 等）。项目里它是个"预备役"——KDJ 因为口径问题手写了，TA4J 留给未来新增的指标。你需要知道的是它的核心抽象 `BarSeries`（K 线序列）和我们引擎里 `Candle` 记录的对应关系。

**KDJ 指标。** 随机指标，判断超买超卖。计算链条：先算 RSV（未成熟随机值，当日收盘价在最近 9 日最高价最低价区间中的位置，0-100），然后 K = SMA(RSV, 3, 1)、D = SMA(K, 3, 1)、J = 3K - 2D。金叉（K 上穿 D 且处于低位区，我们定 K ≤ 20）被视为买入参考，死叉（K 下穿 D 且 K ≥ 80）视为卖出参考。项目里的精确语义冻结在 `docs/architecture.md`，实现是 `stock-engine` 的 `KdjCalculator`——不到 60 行，配了 13 个单元测试，用人工推演过的合成 K 线验证交叉日期。

**Strategy SPI。** SPI 是 Java 的服务提供者接口机制（Service Provider Interface），简单说就是"定义接口、运行时按名字找实现"的插件机制，JDBC 驱动就是这么加载的。项目里 `Strategy` 接口是策略的代码级逃生舱：配置驱动的策略（YAML 里写 `type: kdj_cross` 加参数）覆盖不了的复杂策略，可以实现这个接口写 Java 插件。V1 只定义了接口没做动态加载——这是刻意的，"扩展点留缝不留洞"。

**前复权（qfq）。** 股票分红送股后，历史价格会"跳水"，不复权的话均线、指标全部失真。复权就是对历史价格做数学调整让走势连续：前复权是以最新价为基准往前调，后复权是以最早价为基准往后调。项目统一用前复权（akshare 的 `adjust="qfq"`），因为信号判断永远站在"今天"往回看。每张行情表里都落了 `adjust` 和 `source` 字段，保证数据口径可追溯。

### 2.3 数据层（Python 那一小截）

**akshare。** Python 的开源金融数据库，可以理解为"Python 界的免费行情 SDK"。它本身不产生数据，是把东方财富、新浪、腾讯、中证指数官网这些公开网页接口封装成了干净的函数：`ak.stock_zh_a_hist(symbol="600519", adjust="qfq")` 一行拿到贵州茅台三年的前复权日线。类似的库还有 Tushare（积分制，A股强、港美弱）和 easyquotation（偏实时快照）。选 akshare 是因为四个市场覆盖最全、免费、活跃维护。代价前面说过了：它依赖的网页接口没有 SLA，会限流会改格式，所以抓取层必须做容错。

**三源切换与健康记忆。** `fetch_batch.py` 的源优先级是东财 → 新浪 → 腾讯，东财连续失败两次后记忆翻转，优先用备用源。这个"健康记忆"是个五行的状态变量，但把全量抓取时间从 3.75 小时压回了 40 分钟——没有它的话，300 只股票每只都要先白等东财失败三次的 35 秒退避。

**断点续灌。** 批量抓取前先查数据库里这只股票的 `MAX(trade_date)`，从最新日期的下一天开始抓；写入一律 upsert。脚本跑到一半被杀，重跑自动从断点继续，不产生重复行。

### 2.4 前端层（你不一定熟，展开讲）

**Vue 3（全局构建版，无 npm）。** Vue 是前端三大框架之一（React、Vue、Angular），核心思想是数据驱动视图：JS 对象变了，页面自动跟着变，不用手动操作 DOM。现代前端工程的标准玩法是 npm + 构建工具 + 单文件组件，但项目用的是**全局构建版**——一个 `vue.global.prod.min.js` 文件直接 `<script>` 引入，`Vue.createApp({...}).mount('#app')` 就跑起来了，零构建链。对"一个页面加一个图表"的规模，工程化是杀鸡用牛刀；而且你是 Java 工程师，不欠 npm 那套工具链的学习债。

**ECharts。** 百度开源的图表库，国内金融图表的事实标准。项目里画两块图：收盘价走势线和 K/D/J 三条线，双 grid 上下排列，悬浮提示（tooltip）按日期吸附显示当天数值。ECharts 的 `axisPointer.link` 可以把两个图的悬浮联动到同一天。

**一个真实踩过的 Vue 坑**：ECharts 实例不能放进 Vue 的 `data()`。Vue 3 会把 data 里的对象包成响应式 Proxy（代理对象，拦截读写实现变更追踪），ECharts 实例被代理后内部状态会错乱——症状是图表能渲染但悬浮提示死活不出来。修法是实例存到非响应式属性（`this._chart`）。这个坑在 Vue 社区属于"每个新手都会踩一次"级别。

**CSP（Content-Security-Policy）。** 浏览器安全头，告诉浏览器"这个页面允许从哪些来源加载脚本/样式/图片"。它的价值是防 XSS：攻击者注入的脚本因为来源不在白名单里，浏览器拒绝执行。项目是经典的一波三折：第一版 CSP 没放行内联脚本，把整个应用拦死；改成外部脚本后，又被 Vue 模板编译器的 `new Function()` 触发 eval 禁令，继续白屏；最终配置是 `script-src 'self' 'unsafe-eval'`——只允许同源脚本，但放行 eval（Vue 编译模板要用）。经验教训前面说了：**安全头必须对着应用的实际行为配，配完用真实浏览器验证。**

**defer。** `<script defer>` 表示脚本等 HTML 解析完再执行，且多个 defer 脚本严格按声明顺序执行。项目里靠它保证 vue → echarts → app.js 的执行顺序，不需要任何加载器。

**为什么前端资源要自托管（vendor 目录）。** 最初 Vue/ECharts 从 jsdelivr 等公共 CDN 加载，后来全部下载到 `static/vendor/`。两个理由：国内访问 jsdelivr 不稳定（你父亲的手机网络可能就是打不开），以及 CSP 可以收紧到 `script-src 'self'` 最严一档。

### 2.5 运维层（Java 工程师最容易陌生的一层）

**systemd。** Linux 的系统和服务管理器，相当于 Windows 的服务管理器加任务计划的总和。项目里它负责：应用开机自启（`systemctl enable`）、崩溃自动重启（`Restart=on-failure`）、环境变量注入（`EnvironmentFile`）、日志收集（`journalctl -u stock-signal`）。两个必记特性：EnvironmentFile 不认 `export` 前缀（踩坑一）；`journalctl` 是查日志的唯一入口，应用崩溃先 `journalctl -u stock-signal --no-pager | tail -50`。

**Caddy。** 现代 Web 服务器/反向代理，对标 Nginx。和 Nginx 的区别：配置极简（我们的整个反代配置十行）、**自动申请和续期 HTTPS 证书**（内置 Let's Encrypt 客户端，域名指过来就自动签，Nginx 要另装 certbot 配定时任务）。项目里它做三件事：反向代理（域名 443 → 应用 8080）、HTTPS 终止、下发安全响应头。对单应用小项目，Caddy 的体验全面优于 Nginx。

**cron。** Linux 定时任务。项目的调度设计是"引擎无调度概念，cron 只是触发器"：每天 17:30 和 17:45，cron 各发一个 HTTP POST 到 `/api/daily-runs?market=SH/SZ`，剩下的编排全在 Java 里。这样的好处是调度逻辑可测试、可手动触发（你随时可以自己 curl 一次），不依赖 cron 的上下文。

**mysqldump + 备份策略。** MySQL 官方的逻辑备份工具，把数据库导出成 SQL 文本。每天凌晨 3:15 执行，gzip 压缩，保留 30 天。细节：应用账号没有 PROCESS 权限，要加 `--no-tablespaces` 跳过表空间元数据。备份的价值在部署第一天就被验证过——重装系统时它是数据兜底。

**fail2ban。** 入侵防御小工具：盯着日志里的失败记录（SSH 登录失败、我们的 `AUTH login fail`），同一 IP 失败超阈值就用防火墙封禁一段时间。安装于入侵事件之后，SSH 失败 5 次封 24 小时。它的思路和我们应用内的登录限流（5 次锁 15 分钟）是同一种：让暴力破解的成本高到不值得。

### 2.6 推送与安全层

**PushPlus。** 微信消息推送服务。微信官方不给个人开发者发消息的权限，PushPlus 绕了一步：你微信关注它的服务号，它给你 token，你的系统往它的 webhook 发 HTTP POST，消息就出现在你微信里。免费版每天 200 条够我们用。集成上有一个实测踩出的坑：**PushPlus 业务失败也返回 HTTP 200**，错误码在响应体的 `code` 字段里（比如未实名认证返回 905）——只判断 HTTP 状态码会把失败误判成成功，我们的 `WechatNotifier` 现在同时校验 body 里的 code。这类"HTTP 200 但业务失败"的设计在中国互联网 API 里非常常见，对接任何第三方都要先确认这一点。

**单账号认证。** 系统只有两个人用（你和你父亲），所以是单口令模式：口令存服务器环境变量（`AUTH_TOKEN`），登录时比对，通过后下发 Cookie。Cookie 里不放口令明文，放的是口令加固定盐的 SHA-256 派生值。Cookie 三件套：`HttpOnly`（JS 读不到，防 XSS 窃取）、`Secure`（仅 HTTPS 传输）、`SameSite=Strict`（跨站请求不携带，防 CSRF）。

**登录限流与审计。** 单口令最怕爆破，所以同一 IP 连续失败 5 次锁定 15 分钟（返回 429），成功失败都写审计日志（`AUTH login success/fail ip=...`），格式对齐 fail2ban 的匹配规则，可以联动封 IP。

**幂等与僵死清理。** 前面讲过幂等，这里补一个部署期长出来的机制：防并发运行。冷却期（10 分钟）挡不住"上一次还没跑完"的情况——一次全池 FETCH 要 20 分钟，第 17 分钟再触发就会两个抓取进程并发。所以触发前还检查该市场有没有 RUNNING 状态的阶段。这又引出僵死问题：进程被杀了，RUNNING 记录永远挂着，该市场会被锁死两小时。解法是应用启动时把所有残留 RUNNING 标记为 FAILED（`StaleRunCleanup`）——单实例应用，启动时不可能存在合法的进行中运行。这一串连锁设计是运维系统的典型进化路径：每加一个保护，都会暴露一个新的边界情况。

## 三、横纵交汇：给你的导读路径和下一站的词

### 3.1 按这个顺序读代码，半天看懂全项目

第一步，读 `docs/architecture.md`（10 分钟）。这是全部冻结决策的权威文档，代码行为的"宪法"。

第二步，读 `stock-engine`（1 小时）。这是心脏，而且完全没有框架噪音：`Candle` → `KdjCalculator` → `KdjCrossStrategy` → `Strategy` SPI，配着 13 个单测看，每个测试就是一个使用示例。

第三步，读 `stock-data`（30 分钟）。5 个实体类加 5 个 Mapper 接口加 XML，SQL 全在这里，没有更复杂的了。

第四步，读 `stock-server` 的 `DailyRunService`（1 小时）。四阶段编排是系统的骨架流程，读懂它就读懂了"这套系统每天到底在干什么"。然后顺着看 `FetchRunner`（Java 怎么调 Python）、`WechatNotifier`（怎么发微信）、`AuthService`（认证和限流）。

第五步，读 `fetch/` 的 Python（30 分钟）。`fetch_daily.py` 是单股抓取加三源实现，`fetch_batch.py` 是批量加容错。不懂 Python 语法没关系，它的逻辑简单到猜都猜得出来。

第六步，打开页面看 `static/app.js`（可选）。前半是 Vue 的数据和方法，后半是 ECharts 配置。

### 3.2 下一站：AGENT 分析会碰到的新名词

路线图里的下一阶段是"爬新闻和公司信息，用 LLM 判断对市场的影响"。到时候你会碰到这些词，提前认识一下：

**Spring AI / LangChain4j**：Java 的 LLM 应用框架，封装了各家大模型 API 的调用、Prompt 模板、输出解析。相当于 LLM 界的 Spring——你不用自己拼 HTTP 请求了。**Function Calling / 工具调用**：让 LLM 能"调用"你的 Java 方法（比如"查一下这只股票最近的信号"），模型生成结构化调用请求，框架执行后把结果喂回给模型。**RAG（检索增强生成）**：把新闻/公告切片存进向量库，提问时先检索相关片段再让模型基于片段回答，解决模型不知道最新新闻的问题。**向量库（Vector Store）**：存文本向量的数据库（PGVector、Milvus、Chroma），做语义相似度检索。**MCP（Model Context Protocol）**：Anthropic 推的工具/数据源接入协议，LangChain4j 已支持客户端。

架构上这些都有地方放：信号产出后把上下文丢给一个分析模块——这个扩展点在 V1 的第一天就留好了。
